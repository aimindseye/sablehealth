# Android testing and release qualification methodology

**Status:** normative policy proposal for owner review, 2026-11-27. This document establishes the next implementation requirements. It does not claim that emulator instrumentation, golden screenshots or automated release-device tests already exist or pass. Existing executable gates remain mandatory during migration.

## 1. Repository and delivery discipline

- Canonical checkout: `~/Documents/projects/sablehealth`. Work on a clean, explicitly selected feature branch; record parent, candidate and tracked/untracked state. Temporary worktrees require a reason; do not delete or overwrite existing work.
- One consolidated complete-file ZIP and matching draft PR per implementation deliverable; document apply/verify/rollback, changed files and exact candidate. Owner builds, signs, validates and alone merges. A documentation-only PR need not rebuild or install a previously qualified APK.
- Keep `tools/build-release.sh` as owner-only signing entrypoint. Preserve the existing commit-scoped archive `~/Downloads/sablehealth-release/<version>/<commit>/` and pinned certificate. Record APK SHA-256, package, version and source commit in the release receipt. Never select an APK solely by version or mtime.
- Resolve the Android SDK and paths from the repository or environment, not milestone worktree names or reused shell variables. Fail with actionable missing-path diagnostics. Never reset, clean, uninstall or clear physical app data implicitly.

## 3A. Primary owner-side execution: Ubuntu headless build and signing

Owner decision, 2026-11-27: Ubuntu is the preferred primary execution host for routine builds, full tests, headless Q25 emulation and, after security qualification, owner-authorized release signing. Mac remains the canonical authoring/control checkout, physical USB device station and evidence review console; equivalent Mac execution is an explicit fallback. Hosted GitHub Actions remains independent and mandatory.

### Owner-side paths

- Build source checkout: `/srv/sable-build/sable-health/sablehealth` (this repository). Companion paths are `/srv/sable-build/sable-health/sablehealth` and `/srv/sable-build/sable-health/sablebridge`; do not rename GitHub repositories or packages.
- Shared infrastructure under `/srv/sable-build/sable-health/`: proposed `sdk/`, `avd/`, `gradle-cache/`, `workspaces/`, `test-evidence/`, `unsigned-releases/`, `signed-releases/`. Isolate candidate and application outputs; preserve per-version/per-commit archive identity.
- Owner-designated keystore location: `/srv/sable-build/signing/`. Never commit keystore filenames, contents, passwords or private host details; configuration is local. Existing Mac signed archives and encrypted backup are retained.

### Qualification and security boundary

- Qualify OS/ABI, CPU virtualization and non-root KVM access, RAM, disk headroom, SDK/JDK compatibility, private SSH and workload isolation before provisioning. No changes to existing services, broad ownership/permission changes, or assumptions about host name. Start with one headless Q25 emulator and sequential jobs; resource budgets follow measured capacity. ADB local only; no new public listeners or persistent public-repository self-hosted Actions runner.
- Use separate unprivileged build and signing identities with no broad sudo or shared writable executable paths. Build identity must not read the keystore or alter signing directory ancestors, signer tooling, verified staging or signed outputs. Verify effective permissions, ownership, ACLs, mount and symlink boundaries; trusted owner/admin remains trusted. If the intended directory cannot meet those constraints, hold migration until protected storage is established. Do not run Gradle, repository scripts or untrusted test code as signer.
- Keep the existing registered certificate; owner copies (not deletes original) JKS over private authenticated transfer only after storage and access checks pass. Protect with restrictive permissions and encryption at rest; retain independently recoverable encrypted backup. Passwords entered interactively through a private terminal/SSH session; no stored plaintext, shell arguments, environment secrets, logs or CI credentials. Do not expose signing keys to GitHub, build identity or automated test jobs.
- Mac dispatches reviewed exact commit or reviewed content-addressed source package before push over private SSH. Verify source/tree and clean candidate identity, use isolated run-specific workspaces, bounded execution, safe cancellation and cleanup of only owned processes. No auto-push, auto-merge, arbitrary PR code, root builds or SSH-agent forwarding.
- Ubuntu runs the existing full preflight, Gradle compilation, JVM/Robolectric, static/security checks, native instrumentation, golden screenshot comparison and coverage using qualified KVM and renderer. Automated actions/assertions/captures require no visual supervision; capture failure evidence and sanitize logs. Synthetic data only, no real accounts/health records on emulators.
- Future signing handoff must independently stage a verified immutable copy of the exact unsigned APK and source/evidence manifest outside build-writable paths, verify package/version, unsigned state, hash, required quality/security and exact-head CI evidence, and obtain explicit owner authorization before signing using trusted fixed tools. Verify pinned public certificate and final APK identity; return signed APK, receipt and evidence hashes to Mac over private SSH. Owner alone approves installation/release. A hash identifies bytes, not proof of trustworthy build; host/root compromise remains a shared-key risk.
- Until the remote runner, protected signing boundary and artifact handoff are qualified, existing owner-side build-release scripts, Mac signing and mandatory local preflight remain unchanged. Never bypass checks to reduce resource usage. Ubuntu failure/unavailability means HOLD or explicit equivalent Mac fallback; hosted CI and physical Q25 acceptance remain distinct. No production or acceptance status changes.

## 4. Test layers and implementation requirements

1. **Existing local and CI gates:** retain JVM golden vectors, Robolectric, contract tests, lint, Detekt, ktlint, dependency/security scans, unsigned assembly and Sonar. No blanket suppressions or gate reductions.
2. **Native instrumentation:** add AndroidJUnitRunner, test-only dependencies and a debug-only isolated Compose host; assert a real semantics root attaches within a bounded timeout. Keep the visible test host awake without bypassing keyguard. Render the actual production composables with injected deterministic fixtures, not duplicated mock UI. Add full-app navigation/lifecycle tests as well as isolated component tests. Use centralized stable test tags (Tid); preserve meaningful accessibility content descriptions; expose stable resource IDs for external automation where needed.
3. **Visual regression:** capture fixed synthetic fixture/date/time-zone/locale/theme/font-scale/profile states after assertion and render-idle. Use approved baselines and documented environment-specific tolerances; capture actual/reference/diff on failure. Do not update goldens automatically to pass. Prefer CI-generated baselines for CI and separately qualified local renderers where needed. Assert usable bounds, no clipping or overlap, visible essential controls, >=48dp targets and keyboard focus order. At accessibility scales or with an IME, allow intentional scrolling/pagination rather than clipping.
4. **Coverage:** add actual app instrumented JaCoCo reporting while retaining existing core JVM and app JVM coverage. Generate fresh reports for the exact candidate; validate XML, expected executed classes/source mappings, test counts and failures/skips; reject missing, stale, ambiguous or zero-execution inputs. Combine execution/report data without double counting and preserve line+condition denominator and per-module differential coverage. Send correct module report paths to Sonar; require real quality gate. Minimum 80% new Kotlin/Java line+condition coverage per changed module, Sonar new-code >=80%, Security A, Reliability A, duplication <=3%; retain any stricter existing repository Python or cumulative thresholds. Docs-only changes explicitly have no executable denominator. Never fabricate coverage.
5. **Signed release:** separate external ADB/UI automation targets the already installed release, not an instrumented debug replacement. Resolve the archive by exact installed APK SHA-256 and verify package, source receipt, version, user and device; fail closed on mismatches or unsupported split identity. Automate semantic navigation, clicks, text entry, ordinary scrolls and screenshot capture with bounded waits and screen assertions; no blind fixed coordinate sequences. Capture failure evidence safely, classify automation/navigation errors separately from functional failures. Manual fallback only for unsupported navigation/scrolling, user consent, sensitive permission/system operations or actual wearable actions. Restore only settings changed with explicit consent; never reset data, change security or grant/revoke permissions silently. Mark unsupported/unobserved checks NOT OBSERVED, not PASS.

## 5. Proposed command contract (not implemented by this policy)

From canonical Mac checkout, dispatch full qualification with `bash tools/test-remote.sh --full`; Ubuntu executes `bash tools/test-headless.sh --full` using the same test assertions as hosted CI. Future owner-authorized remote release entrypoint: `bash tools/build-release.sh --remote` (build and isolated signing handoff); preserve existing entrypoint until qualified. Explicit Mac fallback: `bash tools/test-local.sh --unit|--emulator|--visual|--coverage|--full`. Mac physical-device qualification: `bash tools/test-device.sh --q25`. Options denote alternatives. These interfaces are not implemented yet. Existing executable preflight and release gates remain mandatory during migration. CI requires Q25 instrumentation and visual regression for applicable executable PRs after migration; no green claim from documentation, previews, JVM tests alone or skipped jobs.

## 6. Evidence, privacy and acceptance

- Per candidate: record baseline/head, clean source identity, test/profile/environment, expected and executed counts, outcomes, report paths/hashes, coverage and CI status. Distinguish automatic assertions, owner observations and unsupported steps.
- Synthetic data only in CI, repository goldens, logs and uploaded artifacts. No genuine health values, source record IDs, account names/tokens, device serials, private keys, or raw logcat. On physical hardware store screenshots and diagnostics locally with restricted permissions under `~/Downloads/sable-device-evidence-runs/`; do not upload automatically. Review/redact before sharing and preserve hashes for the reviewed package. Do not capture unrelated foreground apps or system screens containing sensitive data.
- CI and emulator evidence do not certify real device behavior. Exact-head green CI and verified owner-side qualification (prefer Ubuntu, explicit Mac fallback) precede owner-signed installation; required physical checks and accepted visual baselines precede release approval. Keep draft/hold until blockers are resolved; no public distribution or security acceptance is inferred.
